# Журнал разговоров Алисы и контекст умного дома — 06.11.2026

## Что включено на физической Лайт 1 «Комната»

На установленном Quasar Bridge включили встроенный `conversation_log` через изменение **только** конфигурации и `SIGHUP`; бинарник, TTS и маршрутизация не менялись.

- Путь на колонке: `/data/opt/quasar-bridge/runtime/conversations.jsonl`.
- `conversation_log.enabled=true`, `max_size_mb=1`, `max_backups=2`, `max_text_chars=16000`.
- Права: каталог `0700`, журнал `0600`; в Git журнал не выгружается.
- В `/healthz` после включения: `conversation_log_enabled=true`, `conversation_log_failures=0`.
- Предыдущая конфигурация: `/data/opt/quasar-bridge/config.before-conversation-log-20261106.json`.
- Свободное место на UBI во время включения: около 11 МБ. Буфер ограничен **3 МБ суммарно**, что не является гарантией хранения за календарный месяц.
- Журнал содержит **текст**, а не сырой звук микрофона или сетевые пакеты.

Встроенный наблюдатель `internal/bridge/conversation.go` фиксирует события `request`, `transcript` (финальное ASR), `route`, `cloud_response`, `progress`, `response` и `cancel` с отметкой времени, идентификаторами сессии/запроса, способом обработки и временем. `response.Delivered=true` означает успешную отправку в WebSocket колонки, **но не доказывает, что речь фактически прозвучала**.

Ограничения: фиксируются реплики после активации, проходящие через UniProxy/Bridge; это **не** постоянная запись всех бытовых разговоров около колонки. Wake-wordless команды отдельного command-spotter/fastcommands — отдельный тракт и пока не интегрированы в единый журнал. При takeover с другим STT протокол `AsrResult` может отсутствовать; нужно отдельное событие от такого обработчика. Эксплуатационные ошибки, фактическое выполнение действий HA и событие старта физического воспроизведения пока не гарантированно связаны с каждой записью.

## Требование на следующий этап: закрытый архив на 30 суток (ещё НЕ внедрён)

Нужен архив вне ограниченной внутренней флеш-памяти Станции, на постоянно доступном домашнем узле, с резервированием на случай кратковременной потери сети. Цель — **30 полных суток**, а не только последние 3 МБ кольцевого журнала.

Рекомендуемая структура: один `YYYY-MM-DD.jsonl.gz` за UTC-день + индекс смещений/идентификаторов для дедупликации при повторном импорте. Проверять целостность строк и сохранение всех событий при ротации `.1/.2`. Файлы только локальные, права владельца, никогда не в публичный GitHub, без raw-аудио. По истечении 30 дней удалять старые архивы; предусмотреть ручное удаление по запросу пользователя.

Не запускать по этому документу автоматически никакие скрипты/планировщики анализа; пользователь отдельно попросил **отложить** еженедельный AI-анализ и создание автоматизаций на основе частых команд.

## Какие данные о Home Assistant давать нейросети

Нужно разделить **справочник устройств** (редко меняется) и **актуальное состояние** (часто меняется). Нельзя считать вчерашнюю яркость или цвет из промпта текущими. Лучше передавать только относящиеся к команде и явно разрешённые Assist сущности.

Пример структуры состояния одной световой сущности (условный, не данные пользователя):

```json
{
  "entity_id": "light.example_hallway",
  "friendly_name": "Свет в прихожей",
  "area": "Прихожая",
  "aliases": ["свет в коридоре"],
  "state": "on",
  "attributes": {
    "brightness": 153,
    "color_mode": "color_temp",
    "color_temp_kelvin": 2700,
    "supported_color_modes": ["color_temp", "hs"],
    "effect": null
  }
}
```

`brightness` нормализован в Home Assistant по шкале 1–255, здесь 153 ≈ 60%. `color_temp_kelvin` в K: чем ниже значение, тем теплее свет. В режиме цветного света передавать его актуальный формат: `hs_color`, `rgb_color`, `xy_color`, `rgbw_color` или `rgbww_color` согласно `color_mode`. Не все атрибуты доступны одновременно и не все лампы поддерживают изменение цвета. `supported_color_modes` и пределы `min_color_temp_kelvin`/`max_color_temp_kelvin` описывают возможности. При `unknown`/`unavailable` не выдавать сохранённый цвет или яркость за текущие значения.

Для климатических устройств важны текущая/целевая температура, `hvac_mode`, `hvac_action`, влажность, пресеты; для штор — позиция в процентах; для вентиляторов — скорость/процент; для датчиков — значение с `unit_of_measurement` и классом измерения. Комнаты и алиасы брать из реестра HA; они могут не входить в объект `state`.

Оптимизация **на будущее**, не внедрена сейчас: обновлять список устройств по изменениям реестра, а динамические атрибуты запрашивать в момент команды; простое распознавание «включи свет в прихожей» отправлять напрямую в HA Intents, без LLM; сложные составные команды и вопросы о состоянии — в LLM с минимальной релевантной выборкой и повторной проверкой доступности/прав до действий.
