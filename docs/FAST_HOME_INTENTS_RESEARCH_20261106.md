# Быстрые команды умного дома без LLM — исследование 06.11.2026

**Статус: opt-in реализация fast-path в исходниках + офлайн-тесты; на физическую колонку НЕ выкачено.** Не заменять штатную прошивку, wake-word, ASR, LED, нативный TTS и плеер. Не запускать второй распознаватель или отдельный LLM-классификатор.

## Что уже умеет существующая архитектура

- `aliced` штатной прошивки может локально распознавать ограниченный набор коротких команд без wake-word и выдавать IPC-события `source=command`. Небольшой существующий обработчик уже принимает две точные фразы («включи свет» / «выключи свет») и вызывает Home Assistant LAN webhook. Он не получает аудиозапись и не использует LLM.
- Для **«Алиса, включи свет в зале»** штатный wake-word и ASR дают финальный `AsrResult`. Quasar Bridge умеет выбирать маршруты по явным правилам без LLM-классификатора, но маршрут `home` в существующем `internal/home/controller.go` **всё ещё вызывает LLM Planner** для большинства действий. Следовательно, добавление маршрута `home` само по себе не создаёт fast-path.
- Для нового безопасного fast-path необходимо распознавать ограниченное, однозначное намерение по **финальному** ASR и передавать его уже существующему HA-интерфейсу **до** LLM. Все несовпавшие или неоднозначные фразы возвращаются текущей маршрутизации, не выключая классификатор целиком.

## Реализованный, но выключенный по умолчанию fast-path

В исходниках канонического Quasar Bridge добавлены:
- `internal/home/fastintent`: чистый Go-парсер только **полных точных** фраз. Возвращает `intent + room + color/temperature/brightness`, не знает адресов HA и не делает действий;
- `internal/bridge/engine.go`: проверяет fast-intent **до** LLM-классификатора в обычном режиме;
- `internal/bridge/native.go`: такой же приоритет для **принудительного Quasar Assistant** (иначе он запускал бы LLM независимо от обычных правил);
- `internal/home/fast.go`: вызывает **существующий** HA MCP без Planner/LLM; проверяет целевой entity ID из allowlist, Assist exposure, отсутствие `unknown/unavailable`, поддержку цвета, результат команды и последующее состояние; при ошибке действия **не повторяет**, чтобы избежать дубля.

Опция **отключена при любой обычной конфигурации**. Для потенциальной опытной установки потребуются все три параметра в *локальном* runtime environment (конкретные endpoint и entity ID — только в приватном runbook, не в Git):
- `QUASAR_HOME_MCP_URL` — адрес уже установленного и проверенного HA MCP; без него `HomeController` вообще не создаётся;
- `QUASAR_FAST_HOME_ENABLED=1` — отдельный opt-in флаг;
- `QUASAR_FAST_HOME_TARGETS_JSON` — объект JSON из ключей `local`, `bedroom`, `living_room`, `kitchen`, `corridor` со строго проверенными значениями `light.*` или `switch.*`. Например, только **синтетическая** конфигурация для тестов: `{"local":"light.example_room","living_room":"light.example_hall"}`. Не выдумывать реальные entity ID.

При отсутствии/повреждении любого из двух fast-параметров команда **не перехватывается** и сохраняется прежний маршрут. `local` — отдельный ключ: команда без комнаты не должна случайно обращаться к залу/кухне из-за эвристики. Команда смены цвета/яркости никогда не маршрутизируется в обычный `switch`. Поддержаны красный RGB(255,0,0), оранжевый RGB(255,95,0), мягкий белый 2700K и яркость 1–100%; это **технические пробные значения**, до настоящего включения можно скорректировать оттенки.

**Важное ограничение:** успешная проверка `on/off` подтверждается повторным чтением HA state; для цвета/яркости проверяется только переход в `on`, поэтому фраза ответа «Команда отправлена» не утверждает, будто точный RGB/процент подтверждён. До реального развёртывания нужны тесты фактических атрибутов и нативного подтверждения коротким штатным сигналом. Сейчас короткий ответ при установленном fast-path всё ещё идёт через штатный UniProxy TTS, не через самодельный звук.

`go test ./...` пройден на Home PC; тесты с поддельным HA проверяют цвет, white temperature, яркость, зоны, отказ без exposure, недоступное устройство, неподтверждённое состояние, отсутствие вызовов LLM/Planner. Физических голосовых тестов после этих изменений **нет**. Для отката экспериментального режима достаточно отключить `QUASAR_FAST_HOME_ENABLED` и штатно перезапустить только Bridge; прошивку `maind` не менять. Журнал `conversations.jsonl` пока пишет маршрут `home` без отдельного поля `fast_intent`, источник можно найти в структурированном runtime slog; отдельная метрика в журнале — следующая доработка.

## Безопасность и приемка

1. Сопоставлять **всю фразу**, а не отдельное слово. Нормализовать регистр, «ё/е», пунктуацию и пробелы, необязательное вежливое обращение. Не запускать по `ASR partial`; отсекать отрицания («не включай»), вопросы («почему красный?») и музыку («включи песню Красный»).
2. Для управления — allowlist безопасных сущностей света, проверка доступности, `conversation`-exposure, типа light/switch, зоны, поддерживаемых `color_mode`. Не направлять цвет на switch. Не трогать технические силовые реле и другие устройства по свободному `switch.*`.
3. Не реализовывать новые звуки: исследовать существующее штатное подтверждение/earcon `maind`. Подтверждать успех только после выполнения действия, при возможности сверять состояние HA. `HTTP 2xx` от webhook не доказывает реального переключения лампы.
4. Тесты сперва offline/dry-run на положительных и отрицательных фразах, затем физические голосовые пробы, измерения ASR→match→HA→ack. Исключить двойное исполнение из двух путей (spotter и UniProxy), сохранить Yandex/LLM fallback и rollback.
5. Для цветов сохранить пользовательские пресеты в конфиге HA/групп, а не кодировать огромный словарь произвольных красок в бинарнике. Смена цвета не должна менять яркость без явного намерения.
6. Не трогать музыку, стоп, громкость, будильники и другие штатные функции. Недоступные или неоднозначные устройства не включать.
